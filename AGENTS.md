# AGENTS.md — «Граф денег» (HackAlem AI, команда «50 Tenge»)

Инструкция для любого агента (Codex, Claude Code и т.д.), работающего в этом
репозитории. Прочитай перед тем, как писать код.

## Контекст

Кейс: по графу транзакций (2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81
seed-клиент — отправные точки расследования по данным организаторов) восстановить структуру
организованной группы. Задача — не «построить граф» (он уже дан), а
**присвоить роль каждому узлу, ранжировать по приоритету проверки и объяснить
почему**. Дедлайн — 5 часов живого хакатона. Полное ТЗ с критериями оценки —
`docs/tz.md`, здесь только то, что должно ограничивать код.

**Перед работой прочитай раздел Plan.md своего потока:** A — §5, B — §6,
C — §7; всем — §3 (владельцы и интерфейсы) и §8 (проверки). Правила,
пороги и формулы там детальнее, чем здесь; при расхождении с этим файлом
спроси координатора, а не выбирай сам.

Сдаём: `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv` (см. схему ниже) +
экран просмотра сети + README + один слайд/диаграмма решения (данные →
метрики → роли → интерфейс) + этот файл поддерживается в актуальном виде.

## Жёсткие запреты — жюри проверяет это механически

- **Никаких хардкод-списков gid.** Роль, кластер, приоритет — только через
  вычисляемые метрики на графе. Захардкоженный «правильный ответ» = кейс
  не засчитан.
- **Никакого чёрного ящика.** У каждой роли — формальное правило или порог
  на конкретной метрике, который можно назвать вслух за 10 секунд. Если
  используете ML — признаки должны быть интерпретируемы, важности признаков
  должны быть объяснимы без ML-образования.
- **Никакого обогащения данных.** Нет ФИО, возраста, пола, дохода, типа
  организации — этого нет в `data/*.parquet`, и придумывать не надо. Только
  структура графа и суммы.
- **Один запуск, без ручных шагов.** От сырых `data/*.parquet` до всех трёх
  CSV — одна команда, < 5 минут, на обычном ноутбуке, без GPU/облака.
- **Схема выгрузок фиксирована.** Обязательные колонки (см. ниже) нельзя
  переименовывать/удалять. Добавлять свои — можно.
- **Формулировки — гипотезы, не обвинения.** «Признаки консолидации», не
  «виновен». Данные обезличены (gid — синтетический id), не пытаться
  деанонимизировать.

## Четыре ловушки данных — не игнорировать молча

1. **`out_deg == 0` на `depth == 4` — это обрыв обхода, не доказательство, что
   деньги осели.** 444 узла так устроены. Наивное правило
   `out_deg==0 ⇒ terminal` даст 444 ложных «стока». Если узел имеет
   `out_deg==0`, но `depth < 4` — это гораздо более сильный сигнал настоящего
   получателя без дальнейших наблюдаемых переводов. Это не доказывает
   удержание денег: другие банки, периоды и суммы ниже порога не видны.
   На границе допустим `consolidator` по числу отправителей и входящей
   сумме, без использования отсутствующего выхода как признака удержания.
   **Роль `terminal` на обрыве (depth=4, out_deg=0) не назначать** — только
   `consolidator` с оговоркой или `peripheral` (`role_rule` =
   `boundary_consolidator` / `boundary_unknown`).
   Всегда сохраняйте пометку обрыва и учитывайте её в `role_score`.
2. **У seed-клиентов входящие суммы занижены.** Граф собран *от* seed по
   исходящим переводам — то, что seed получил извне выборки, не в данных.
   `pass_through` у seed бывает кратно больше 1 — это устройство выгрузки,
   а не доказанная аномалия. Не стройте роль seed-узла на «сколько получил».
   Входы извне выборки могут отсутствовать у любого узла. Отношение
   «отправил / получил» описывает только наблюдаемые потоки; совпадение
   сумм не доказывает передачу тех же денег. При нулевом входе отношение
   не определено; не заменять его нулём для назначения роли.
3. **Порог 5 000 KZT.** Дробление сумм ниже порога невидимо в данных — не
   утверждать, что его нет, только что оно не наблюдаемо.
4. **Граф направленный и взвешенный, сеть не монолитна.** По исследованию,
   записанному в Plan.md: 16 компонент с рёбрами и 19 изолятов, всего 35
   слабосвязных компонент полного графа; крупнейшая на 1 877 узлов
   (46 seed), вторая на 270. Пересчитать при загрузке; добавлять в граф
   все gid из nodes.parquet, включая изоляты. Если
   используете неориентированные методы (кластеризация) — оговаривайте это
   явно и не теряйте направление денег там, где оно важно (роли, приоритет).
   Betweenness считать с `weight=None`: сумма перевода — не длина пути,
   с `weight='sum_kzt'` крупные переводы ошибочно становятся «дальними».

## Карта репозитория и границы модулей

Три параллельных потока работы. У каждого файла один владелец; общая
директория pipeline/ разделена по файлам. Plan.md задаёт порядок реализации.

```
data/                  сырые parquet (не трогать)
starter/               код и README от организаторов (не трогать, можно читать)
pipeline/
  __init__.py          пакет                                       [Поток A]
  io.py                загрузка + sanity-check                      [Поток A]
  graph.py             сборка nx.DiGraph                            [Поток A]
  features.py          метрики узлов (degree/pagerank/betweenness/wcc)  [Поток A]
  roles.py             пороги, assign_roles(), evidence-тексты      [Поток A]
  seeds.py             seed_reach_count, seed_distance (BFS от seed) [Поток B]
  clusters.py          cluster_id, гипотезы по кластерам            [Поток B]
  priority.py          priority_score, top_nodes                   [Поток B]
  outputs.py           запись трёх CSV + проверка контракта         [Поток B]
viz/                   экран просмотра (поиск по gid, роли/кластеры) [Поток C]
run.py                 точка входа: один запуск от parquet до CSV   [Поток C]
README.md              квикстарт, критерии ролей, ограничения, масштабирование [Поток C]
docs/scheme.*          один слайд/диаграмма: данные→метрики→роли→интерфейс [Поток C]
docs/roles.md          правила, оценки, ограничения и проверки      [Поток A]
docs/ranking.md        кластеры, формула приоритета и проверки       [Поток B]
docs/status-a.md       готовность и передача результата A           [Поток A]
docs/status-b.md       готовность и передача результата B           [Поток B]
docs/status-c.md       готовность и передача результата C           [Поток C]
tests/test_io.py, tests/test_roles.py                               [Поток A]
tests/test_clusters_priority.py, tests/test_outputs.py             [Поток B]
Dockerfile, compose.yaml, .dockerignore, .gitignore                  [Поток C]
requirements*.txt, AGENTS.md, Plan.md                               [Поток C]
out/                   выгрузки пайплайна (генерируется, в git не класть)
```

Нагрузка выровнена: A — аналитическое ядро (признаки + роли); B —
seed-метрики, кластеры, приоритет и выгрузки с проверкой контракта; C —
точка входа, экран, README, диаграмма, окружение. Первыми сдаются
`features.py` (A) и `seeds.py` (B) — в первые 30–40 минут, чтобы
остальные работали на настоящих признаках. За временем следит
координатор команды, не C.

Поток A (граф/роли) и поток B (кластеры/приоритет) работают над общим
DataFrame — контракт по колонкам зафиксирован ниже, чтобы не блокировать
друг друга. `run.py` (C) соединяет `compute_features` (A) и
`compute_seed_reach` (B) по gid перед `assign_roles`. Поток C не трогает `roles.py`/`clusters.py`/`priority.py` —
только читает готовые CSV и `graph.py` для отрисовки рёбер.
А и B пишут готовые объяснения в свои docs-файлы; C добавляет в README
краткие формулы и ссылки. Изменение чужого модуля согласуется с владельцем.

## Контракт данных

### Вход (`data/*.parquet`, схема — `starter/README.md`)
- `edges.parquet`: `src, dst, sum_kzt, n_tx, depth` — агрегировано за период
- `nodes.parquet`: `gid, depth, is_seed`
- `transactions.parquet`: `src, dst, date, sum_kzt` — не используется в
  базовом пайплайне, нужен только для бонусных временных паттернов

### Общий DataFrame между потоком A и B (после `features.py` + `roles.py`)
Обязательные колонки на этом этапе: `gid, depth, is_seed, in_deg, out_deg,
in_kzt, out_kzt, in_tx, out_tx, pagerank, betweenness, pass_through,
truncated_by_depth, wcc_id, seed_reach_count, seed_distance,
role, role_score, role_rule, evidence` (`seed_reach_count`,
`seed_distance` приходят из `seeds.py` потока B, остальные признаки — от A).
Поток B добавляет `cluster_id, priority_score, priority_volume,
priority_bridge, priority_seed, priority_degree`; последние четыре —
взвешенные вклады, сумма которых равна priority_score.
Таблицы соединять по уникальному gid, без скрытой мутации входа.
NaN допускается для неопределённого pass_through и недостижимого
seed_distance, но не в обязательных полях CSV. Метрики, имя правила и
вклады сохранять дополнительными колонками nodes_roles.csv для карточки.
Меняете контракт — уведомите A/B/C; C обновляет эту секцию и Plan.md.

### Выход — три CSV, обязательные колонки

**`nodes_roles.csv`** — ровно 2 248 строк:
`gid (int64), role (str, из словаря ниже), role_score (float 0..1),
cluster_id (int), priority_score (float 0..1), evidence (str, ≤200 символов,
непустой, с числами, не «высокий скор»)`

Словарь ролей: `consolidator, transit, distributor, terminal, coordinator,
peripheral` (расширять можно, но задокументировать в README).

**`clusters.csv`** — строка на кластер:
`cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`

**`top_nodes.csv`** — ≥20 строк, отсортировано по приоритету:
`rank, gid, role, priority_score, why`

## Как запускать и проверять себя

Целевая команда после реализации (сейчас Docker запускает только starter):

```bash
python run.py --data data --out out
```

Перед тем как считать модуль готовым, агент проверяет:
- `out/nodes_roles.csv` — 2 248 строк, все обязательные колонки заполнены,
  `evidence` непустой и ≤200 символов
- `out/clusters.csv` — `cluster_id` есть у каждого узла из `nodes_roles.csv`
- `out/top_nodes.csv` — ≥20 строк
- полный прогон от сырых parquet до трёх CSV укладывается в 5 минут

## Совместная работа с агентами

- Задача агенту содержит поток, разрешённые файлы, результат и критерии
  готовности. Выполнять реализацию, запуск, исправления и отчёт по результату.
- Каждый участник работает в своей рабочей копии/ветке. При общей файловой
  системе использовать отдельные worktree или строгие границы файлов;
  не переключать общую ветку во время чужой работы.
- Первый сквозной запуск — к концу первого часа; затем интеграция каждые
  45–60 минут. Общие зависимости и точку входа меняет C.
- В docs/status-a.md, status-b.md, status-c.md каждый владелец кратко
  фиксирует готовое, команды и результат проверок, проблемы и следующий шаг.
  Статус «готово» требует результата запуска; план проверки им не является.
- После интеграции A проверяет формулу приоритета B, B — правила A;
  замечания передаются владельцу. C проверяет весь сценарий по README.
- За последний час добавлять бонус только при выполненных must-have;
  последние 20 минут — исправления и репетиция, без новых функций.

## Демо и сдача

Must-have №3 проверяется так: «жюри называет 3 произвольных gid — команда за
минуту объясняет роль». Жюри не обязано спрашивать именно автора `roles.py` —
спросить могут любого из трёх. Поэтому за 5–10 минут до сдачи все трое, не
только Поток A, должны пройтись по финальным порогам ролей, логике кластеров
и формуле приоритета и суметь объяснить любой gid из выгрузок — это не
код-ревью, а разовый common-knowledge проход перед демо.

## Стиль

- `evidence`/`hypothesis`/`why` и вообще любой текст для аналитика — на
  русском, с конкретными числами из данных, а не общими словами.
- Код и идентификаторы — как удобнее автору модуля (английский — ок).
- Не добавлять абстракций/фреймворков сверх необходимого для 5-часового
  хакатона — простой read → compute → write пайплайн.
- Маленькие коммиты, привязанные к своему потоку (A/B/C), мержить в main
  каждые ~45–60 минут, не одним большим коммитом в конце.
