# AGENTS.md — «Граф денег» (HackAlem AI, команда «50 Tenge»)

Инструкция для любого агента (Codex, Claude Code и т.д.), работающего в этом
репозитории. Прочитай перед тем, как писать код.

## Контекст

Кейс: по графу транзакций (2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81
seed-клиент — известные курьеры по наркоделу) восстановить структуру
организованной группы. Задача — не «построить граф» (он уже дан), а
**присвоить роль каждому узлу, ранжировать по приоритету проверки и объяснить
почему**. Дедлайн — 5 часов живого хакатона. Полное ТЗ — у координатора
команды, здесь только то, что должно ограничивать код.

Сдаём: `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv` (см. схему ниже) +
экран просмотра сети + README + этот файл поддерживается в актуальном виде.

## Жёсткие запреты — жюри проверяет это механически

- **Никаких хардкод-списков gid.** Роль, кластер, приоритет — только через
  вычисляемые метрики на графе. Захардкоженный «правильный ответ» = кейс
  не засчитан.
- **Никакого чёрного ящика.** У каждой роли — формальное правило или порог
  на конкретной метрике, который можно назвать вслух за 10 секунд. Если
  используете ML — признаки должны быть интерпретируемы, важности признаков
  должны быть объяснимы без ML-образования.
- **Никакого обогащения данных.** Нет ФИО, возраста, пола, дохода, типа
  организации — этого нет в `data/*.parquet`, и придумывать не надо. Только
  структура графа и суммы.
- **Один запуск, без ручных шагов.** От сырых `data/*.parquet` до всех трёх
  CSV — одна команда, < 5 минут, на обычном ноутбуке, без GPU/облака.
- **Схема выгрузок фиксирована.** Обязательные колонки (см. ниже) нельзя
  переименовывать/удалять. Добавлять свои — можно.
- **Формулировки — гипотезы, не обвинения.** «Признаки консолидации», не
  «виновен». Данные обезличены (gid — синтетический id), не пытаться
  деанонимизировать.

## Четыре ловушки данных — не игнорировать молча

1. **`out_deg == 0` на `depth == 4` — это обрыв обхода, не доказательство, что
   деньги осели.** 444 узла так устроены. Наивное правило
   `out_deg==0 ⇒ terminal` даст 444 ложных «стока». Если узел имеет
   `out_deg==0`, но `depth < 4` — это гораздо более сильный сигнал настоящего
   конечного получателя (обход мог продолжиться, но переводов дальше нет).
   Различайте эти два случая явно и в роли, и в `role_score`.
2. **У seed-клиентов входящие суммы занижены.** Граф собран *от* seed по
   исходящим переводам — то, что seed получил извне выборки, не в данных.
   `pass_through` у seed бывает кратно больше 1 — это устройство выгрузки,
   а не аномалия. Не стройте роль seed-узла на «сколько получил».
3. **Порог 5 000 KZT.** Дробление сумм ниже порога невидимо в данных — не
   утверждать, что его нет, только что оно не наблюдаемо.
4. **Граф направленный и взвешенный, сеть не монолитна.** 16 слабосвязных
   компонент — крупнейшая на 1 877 узлов (46 seed), вторая на 270. Если
   используете неориентированные методы (кластеризация) — оговаривайте это
   явно и не теряйте направление денег там, где оно важно (роли, приоритет).

## Карта репозитория и границы модулей

Три параллельных потока работы — каждый живёт в своей директории, чтобы
агенты не редактировали одни и те же файлы одновременно.

```
data/                  сырые parquet (не трогать)
starter/               код и README от организаторов (не трогать, можно читать)
pipeline/
  io.py                загрузка + sanity-check                      [любой]
  graph.py             сборка nx.DiGraph                            [любой]
  features.py          метрики узлов (degree/pagerank/hits/betweenness/wcc)  [Поток A]
  roles.py             пороги, assign_roles(), evidence-тексты      [Поток A]
  clusters.py          cluster_id, гипотезы по кластерам            [Поток B]
  priority.py          priority_score, top_nodes                   [Поток B]
  outputs.py           запись трёх CSV в фиксированной схеме        [любой, менять осторожно]
viz/                   экран просмотра (поиск по gid, роли/кластеры) [Поток C]
run.py                 точка входа: один запуск от parquet до CSV   [Поток C]
README.md              квикстарт, критерии ролей, ограничения, масштабирование [Поток C]
out/                   выгрузки пайплайна (генерируется, в git не класть)
```

Поток A (граф/роли) и поток B (кластеры/приоритет) работают над общим
DataFrame — контракт по колонкам зафиксирован ниже, чтобы не блокировать
друг друга. Поток C не трогает `roles.py`/`clusters.py`/`priority.py` —
только читает готовые CSV и `graph.py` для отрисовки рёбер.

## Контракт данных

### Вход (`data/*.parquet`, схема — `starter/README.md`)
- `edges.parquet`: `src, dst, sum_kzt, n_tx, depth` — агрегировано за период
- `nodes.parquet`: `gid, depth, is_seed`
- `transactions.parquet`: `src, dst, date, sum_kzt` — не используется в
  базовом пайплайне, нужен только для бонусных временных паттернов

### Общий DataFrame между потоком A и B (после `features.py` + `roles.py`)
Обязательные колонки на этом этапе: `gid, depth, is_seed, in_deg, out_deg,
in_kzt, out_kzt, pagerank, betweenness, pass_through, truncated_by_depth,
role, role_score, evidence`. Поток B добавляет `cluster_id, priority_score`.
Меняете список — правите эту секцию в том же PR/коммите.

### Выход — три CSV, обязательные колонки

**`nodes_roles.csv`** — ровно 2 248 строк:
`gid (int64), role (str, из словаря ниже), role_score (float 0..1),
cluster_id (int), priority_score (float 0..1), evidence (str, ≤200 символов,
непустой, с числами, не «высокий скор»)`

Словарь ролей: `consolidator, transit, distributor, terminal, coordinator,
peripheral` (расширять можно, но задокументировать в README).

**`clusters.csv`** — строка на кластер:
`cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`

**`top_nodes.csv`** — ≥20 строк, отсортировано по приоритету:
`rank, gid, role, priority_score, why`

## Как запускать и проверять себя

```bash
python run.py --data data --out out
```

Перед тем как считать модуль готовым, агент проверяет:
- `out/nodes_roles.csv` — 2 248 строк, все обязательные колонки заполнены,
  `evidence` непустой и ≤200 символов
- `out/clusters.csv` — `cluster_id` есть у каждого узла из `nodes_roles.csv`
- `out/top_nodes.csv` — ≥20 строк
- полный прогон от сырых parquet до трёх CSV укладывается в 5 минут

## Стиль

- `evidence`/`hypothesis`/`why` и вообще любой текст для аналитика — на
  русском, с конкретными числами из данных, а не общими словами.
- Код и идентификаторы — как удобнее автору модуля (английский — ок).
- Не добавлять абстракций/фреймворков сверх необходимого для 5-часового
  хакатона — простой read → compute → write пайплайн.
- Маленькие коммиты, привязанные к своему потоку (A/B/C), мержить в main
  каждые ~45–60 минут, не одним большим коммитом в конце.
