# Поток A: метрики, роли и ограничения

Реализация следует `Plan.md` §5 без изменения порогов и формул. Роль —
гипотеза о наблюдаемой структуре переводов. `role_score` — эвристическая
сила признаков, не вероятность причастности и не измеренная точность.

## Подключение модулей

```python
from pipeline.io import load_data, validate_inputs
from pipeline.graph import build_graph
from pipeline.features import compute_features
from pipeline.roles import assign_roles, compute_role_thresholds

nodes, edges, transactions = load_data("data")
validate_inputs(nodes, edges, transactions)
G = build_graph(nodes, edges)
features = compute_features(G, nodes)
# Следующие строки требуют готового pipeline/seeds.py потока B:
from pipeline.seeds import compute_seed_reach
seed_df = compute_seed_reach(G, nodes)
joined = features.merge(seed_df, on="gid", how="left", validate="one_to_one")
roles = assign_roles(joined)
thresholds = roles.attrs["role_thresholds"]
```

Возвращаемые таблицы не изменяют входные. В граф добавляются все gid,
включая изоляты. Узлы и рёбра добавляются в стабильном порядке; при
перемешивании строк входа численные результаты воспроизводимы в проверенном
окружении. Строки таблицы признаков следуют порядку `nodes`; объединять по gid.

`assign_roles` требует seed-метрики B и не подменяет их нулями. Отсутствующая
колонка или пропуск `seed_reach_count` после неудачного объединения — ошибка.
`seed_distance` сохраняется для карточки, но непосредственно в правиле роли
не участвует.

Валидация входа проверяет схемы, типы идентификаторов/количеств, пропуски,
уникальность gid и пар рёбер, известность концов рёбер, глубину 0..4,
конечные положительные суммы, положительные количества и ISO-даты.
Агрегаты транзакций сравниваются с рёбрами по парам, количествам и суммам
(`rtol=1e-12`, `atol=1e-6 KZT`). Одинаковые строки транзакций не удаляются:
одинаковые переводы в один день могут быть отдельными операциями.
Число узлов не зашито в алгоритм: 2 248 проверяется в тесте предоставленного набора.

## Признаки

| Поле | Расчёт и интерпретация |
|---|---|
| `in_deg`, `out_deg` | Число разных отправителей / получателей |
| `in_kzt`, `out_kzt` | Сумма наблюдаемых входящих / исходящих переводов |
| `in_tx`, `out_tx` | Сумма `n_tx` по входящим / исходящим рёбрам |
| `in_avg_kzt`, `out_avg_kzt` | Дополнительные необязательные поля: сумма / число переводов; NaN при нулевом количестве |
| `pagerank` | Направленный PageRank по `sum_kzt`, alpha=0.85, tol=1e-10, max_iter=1000 |
| `betweenness` | Точное нормированное направленное посредничество, `weight=None`, расстояние в переходах |
| `pass_through` | `out_kzt / in_kzt`; NaN при нулевом входе |
| `truncated_by_depth` | `depth == 4 and out_deg == 0` |
| `wcc_id` | Номер слабосвязной компоненты; сортировка по убыванию размера, затем минимальному gid |
| `seed_reach_count` | От B: число разных seed, достигающих узел за 1–4 направленных шага; сам узел не учитывается |
| `seed_distance` | От B: минимальная направленная дистанция; 0 для seed, NaN для недостижимого узла |

Сумма на ребре не используется как длина пути. PageRank, в отличие от
betweenness, учитывает объём. Изолят может иметь положительный PageRank из-за
телепортации; это не наблюдаемая денежная связь и не основание назначить роль.

NaN для неопределённых отношений допустим в дополнительных метриках, но
не в `role`, `role_score`, `role_rule`, `evidence`.

## Пороги и порядок ролей

`Q75` — линейный 75-й процентиль положительных `in_kzt` среди non-seed.
`Q95` — линейный 95-й процентиль положительного betweenness по всем узлам.
На пустой выборке порог равен `None`, и соответствующее правило выключено.
На предоставленных данных получены:

- `in_kzt_q75 = 165000.0` KZT;
- `betweenness_q95 = 0.0013361804007553844`.

Пороги вычисляются заново при каждом вызове, не зашиты как ответы. Получить
их можно через `compute_role_thresholds(joined)` или `roles.attrs['role_thresholds']`.
C следует сохранить их в метаданных запуска до дальнейших объединений:
`DataFrame.attrs` не переносится в CSV автоматически. В коротких объяснениях
числа форматируются, а сравнение в алгоритме использует полную точность.

Правила применяются сверху вниз. Первое совпавшее определяет основную роль;
`role_rule` сохраняет причину выбора.

| `role_rule` | Роль | Условие |
|---|---|---|
| `isolated` | peripheral | Входящая и исходящая степень равны 0 |
| `boundary_consolidator` | consolidator | Обрыв; non-seed; вход от ≥3 отправителей; входящая сумма ≥Q75 |
| `boundary_unknown` | peripheral | Остальной узел на обрыве |
| `coordinator` | coordinator | Non-seed; есть вход и выход; seed-достижимость ≥2; betweenness ≥Q95 |
| `consolidator` | consolidator | Non-seed вне обрыва; входящая степень ≥3 и ≥2×max(исходящая степень,1); входящая сумма ≥Q75 |
| `distributor` | distributor | Исходящая степень ≥5; для non-seed также ≥2×max(входящая степень,1) |
| `terminal` | terminal | Non-seed; есть вход; исходящих 0; глубина <4 |
| `transit` | transit | Non-seed; есть вход и выход; отношение выхода к входу в [0.7;1.3] включительно |
| `fallback` | peripheral | Предыдущие правила не сработали |

У `terminal` проверка отсутствия консолидации обеспечивается порядком.
`coordinator` может перекрыть distributor/transit: это объявленный выбор
основной роли. Число кандидатов до применения порядка доступно в
`roles.attrs['role_candidate_counts']`; кандидаты могут пересекаться.

## Формулы score

`E(x,t) = clip((x/t − 1)/2, 0, 1)` для положительного порога t.
На пороге E=0, при тройном превышении E=1. При отсутствующем пороге
E=0, соответствующее правило уже выключено.

| Роль / правило | Оценка |
|---|---|
| consolidator | `0.55 + 0.15*E(in_deg,3) + 0.15*E(in_kzt,Q75)` |
| boundary_consolidator | Та же формула минус 0.15 |
| distributor | `0.55 + 0.30*E(out_deg,5)` |
| coordinator | `0.45 + 0.15*E(betweenness,Q95) + 0.15*E(seed_reach_count,2)` |
| transit | `0.45 + 0.20*clip(1 − abs(pass_through−1)/0.3, 0, 1)` |
| terminal | 0.55 |
| fallback / boundary_unknown / isolated | 0.20 / 0.15 / 0.10 |

Оценка рассчитывается после выбора роли. Сумма не повышает уверенность
в удержании денег у terminal. Seed может получить distributor по выходу;
его вход и pass_through не определяют ни эту роль, ни её score.

## Ограничения и формулировки

- На обрыве не назначается terminal. Консолидация там опирается только на
  входящие признаки; неизвестный выход явно указан в evidence.
- Terminal означает отсутствие дальнейших наблюдаемых переводов внутри
  охвата, а не доказанное хранение денег. Другие периоды и банки не видны.
- У любого узла могут отсутствовать внешние входы, особенно у seed.
  Близкие суммы входа и выхода не доказывают передачу тех же денег.
- Coordinator — гипотеза о структурном связующем узле, не доказательство
  руководства группой. Достижимость от seed не доказывает путь конкретных денег.
- Peripheral объединяет неопределённые случаи: это не доказанная
  периферийность, невиновность или низкая полезность проверки.
- Переводы ниже 5 000 KZT невидимы; отсутствие дробления утверждать нельзя.
- Нет размеченных ролей: accuracy и статистическая калибровка score не заявляются.

`evidence` строится русскими шаблонами с числами и ограничениями, никогда
не обрезается. Нарушение длины 1..200 символов выдаёт ошибку. Пример из
рассчитанного результата без фиксации gid в правилах:

> Признаки консолидации: вход от 3 (≥3), 555 000 KZT (Q75=165 000); depth=4, обрыв обхода; дальнейший выход неизвестен.

Тесты покрывают валидацию, изоляты, направленность, разделение веса и
расстояния, точные границы правил, пустые выборки квантилей, нулевой вход,

изменение и насыщение score, длину evidence и отсутствие мутаций.

полей роли, score и evidence, а также точное повторение результата при
перемешивании входных строк. Для отсутствующего пока модуля B тест
считает **эталонную seed-достижимость обратным BFS** в тестовом коде.
