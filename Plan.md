## 2. Основное решение и стек

Строим локальный объяснимый пайплайн: **parquet → направленный граф → признаки → правила ролей + сообщества → приоритет → CSV → экран аналитика**.

| Задача | Выбор | Почему |
|---|---|---|
| Загрузка и таблицы | Python, pandas, PyArrow, NumPy | Совместимо со стартовым кодом и форматом данных |
| Граф и алгоритмы | NetworkX, SciPy для вычислительных зависимостей | Размер графа небольшой; простой код, понятные алгоритмы |
| Назначение ролей | Детерминированные правила | Каждую роль можно объяснить метрикой и порогом |
| Сообщества | Взвешенный Louvain внутри слабосвязных компонент | Разбивает большую компоненту на обозримые группы |
| Приоритет | Взвешенная сумма нормированных признаков | Видно, какие факторы подняли узел в рейтинге |
| Интерфейс | Streamlit + PyVis | Быстро сделать поиск, таблицы, карточку и граф со стрелками |
| Проверки | pytest + интеграционная проверка CSV | Проверяем ловушки данных и обязательный контракт |
| Диаграмма решения | Mermaid в `docs/scheme.md`, экспорт SVG/PNG для слайда | Простая схема, воспроизводимая вместе с кодом |

Не включаем в обязательную часть LLM, GNN, обучение классификатора, Neo4j, отдельный API, React и облачное развёртывание. Существующий Docker сохраняем как дополнительный способ запуска, обновляем после готовности пайплайна. Известность seed не даёт разметку остальных ролей, поэтому честной оценки accuracy здесь нет.

По предыдущему исследованию точный направленный betweenness без весов занял **1,87 секунды в окружении исследования**. Используем точный алгоритм для этих данных; это не замер полного будущего пайплайна и не гарантия скорости на любом ноутбуке.

Технологические возможности сверены с документацией: [NetworkX Louvain](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.community.louvain.louvain_communities.html), [Streamlit cache_data](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.cache_data), [PyVis Network](https://pyvis.readthedocs.io/en/latest/documentation.html). Louvain поддерживает веса, resolution и seed; PyVis — направленные рёбра и HTML. Зависимости фиксируем по реально проверенному окружению, а не ставим непроверенные версии накануне демонстрации.

## 3. Разделение между тремя участниками

Общие файлы тоже получают одного владельца: пометка «любой» в AGENTS.md не должна превращаться в одновременное редактирование.

| Участник | Владеет файлами | Результат |
|---|---|---|
| **A — граф и роли** | `pipeline/__init__.py`, `pipeline/{io,graph,features,roles}.py`, `tests/test_roles.py`, `tests/test_io.py`, `docs/roles.md`, `docs/status-a.md` | Полный граф, метрики, роли, оценки, объяснения и их документация |
| **B — seed-метрики, сообщества, приоритет, выгрузки** | `pipeline/seeds.py`, `pipeline/clusters.py`, `pipeline/priority.py`, `pipeline/outputs.py`, `tests/test_clusters_priority.py`, `tests/test_outputs.py`, `docs/ranking.md`, `docs/status-b.md` | seed-достижимость, кластер каждого узла, приоритет, top-30, три CSV с проверкой контракта и их документация |
| **C — интегратор и интерфейс** | `run.py`, `viz/`, `README.md`, `AGENTS.md`, `Plan.md`, `docs/scheme.*`, `docs/status-c.md`, `requirements*.txt`, `.gitignore`, `.dockerignore`, `Dockerfile`, `compose.yaml` | Одна команда запуска, экран аналитика и сборка материалов сдачи |

Нагрузка выровнена: у A — аналитическое ядро на критическом пути, поэтому seed-метрики и выгрузки отданы B, у которого без них основная работа заканчивалась раньше; C освобождён от выгрузок и тестов контракта, так как у него самый широкий объём (экран, README, диаграмма, Docker). Первыми сдаются `features.py` (A) и `seeds.py` (B) — в первые 30–40 минут. За временем следит координатор команды, не C. Участник C интегрирует изменения. A и B сами пишут готовые разделы в docs/roles.md и docs/ranking.md: формулы, пороги, примеры и ограничения. C включает краткие формулы и ссылки в README. Никто не правит чужие модули без согласования. Менять общий контракт можно только с уведомлением всех троих и обновлением AGENTS.md участником C.

Для отдельных рабочих копий: ветки `feat/a-roles`, `feat/b-clusters`, `feat/c-demo`, небольшие коммиты и интеграция каждые 45–60 минут. Если агенты работают в одной файловой системе, нужны отдельные worktree либо строгие границы файлов; нельзя переключать общую рабочую директорию между ветками во время работы других агентов.

### Интерфейсы для реализации — подтвердить в первые 15 минут

```python
# A
load_data(data_dir) -> (nodes, edges, transactions)
validate_inputs(nodes, edges, transactions) -> None
build_graph(nodes, edges) -> nx.DiGraph
compute_features(G, nodes) -> features_df
assign_roles(features_df) -> roles_df

# B
compute_seed_reach(G, nodes) -> seed_df        # gid, seed_reach_count, seed_distance
assign_clusters(G, nodes) -> cluster_map_df     # gid, cluster_id
compute_priority(roles_with_clusters_df) -> scored_df
summarize_clusters(G, scored_df) -> clusters_df
make_top_nodes(scored_df, limit=30) -> top_df
write_outputs(scored_df, clusters_df, top_df, out_dir) -> None   # + проверка контракта

# C
run.py: load → validate → build_graph → features ⋈ seed_df (по gid) → assign_roles
        → clusters → priority → write_outputs
```

Все таблицы узлов содержат уникальный `gid`, соединяются по `gid`, а не по индексу. Функции возвращают новые таблицы без скрытой мутации входа. Роли не зависят от результатов кластеризации: B может разрабатывать сообщества параллельно с A.

Контракт зафиксирован в AGENTS.md, включая `in_tx`, `out_tx`, `wcc_id`, `seed_reach_count`, `seed_distance`, `role_rule`. B добавляет взвешенные вклады `priority_volume`, `priority_bridge`, `priority_seed`, `priority_degree`. B (`outputs.py`) сохраняет эти признаки дополнительными колонками nodes_roles.csv: интерфейс получает готовые метрики и объяснения. `seed_distance` допускает отсутствие значения для недостижимого узла; сам seed имеет расстояние 0. Входящие seed-связи означают только наблюдаемые связи.

## 5. Метрики и роли — участник A

### Признаки первой версии

- Входящие/исходящие степени, суммы и количества транзакций; средняя сумма перевода при ненулевом количестве.
- PageRank с весом `sum_kzt` на направленном полном графе.
- Направленный betweenness с `weight=None`: структурное посредничество по числу переходов. Сумма перевода не является длиной пути; `weight='sum_kzt'` здесь использовать нельзя без иной обоснованной интерпретации.
- `pass_through = out_kzt / in_kzt` при ненулевом входе; для seed не использовать его в назначении роли. У любого узла могут отсутствовать входящие извне выборки. Близость отношения к единице — только наблюдаемый признак возможного транзита, без установления происхождения денег.
- `truncated_by_depth = (depth == 4 and out_deg == 0)`, слабосвязная компонента.
- `seed_reach_count` и `seed_distance` считает B в `seeds.py` (см. §6); правило coordinator берёт их из объединённой таблицы.

HITS, циклы и временные признаки добавляем только после готовности обязательной части. Не перечисляем все простые пути и циклы графа без ограничения.

### Стартовые правила ролей

Правила применять сверху вниз; сохранять имя сработавшего правила. Для пересекающихся признаков выводить одну основную роль и дополнительные наблюдения в карточке. Порядок — часть модели.

| Порядок | Роль | Начальное формальное правило |
|---:|---|---|
| 1 | `peripheral` | Нет входящих и исходящих: наблюдаемой информации недостаточно |
| 2 | `consolidator` или `peripheral` | Если `truncated_by_depth=True`: consolidator при non-seed, `in_deg >= 3` и `in_kzt >= Q75` положительных входов non-seed; иначе peripheral. Всегда пометка границы; исходящие и pass_through не участвуют |
| 3 | `coordinator` | Не seed; есть вход и выход; `seed_reach_count >= 2`; betweenness не ниже Q95 среди положительных значений |
| 4 | `consolidator` | Не seed; `in_deg >= 3`; `in_deg >= 2 * max(out_deg, 1)`; `in_kzt >= Q75` положительных входящих сумм non-seed |
| 5 | `distributor` | `out_deg >= 5`; для non-seed также `out_deg >= 2 * max(in_deg, 1)`; для seed сравнение с входом не применяется |
| 6 | `terminal` | Не seed; `in_deg > 0`, `out_deg == 0`, `depth < 4`; не сработало правило консолидации |
| 7 | `transit` | Не seed; есть вход и выход; `0.7 <= pass_through <= 1.3` |
| 8 | `peripheral` | Остальные: недостаточно признаков выбранных структурных ролей |

`coordinator` здесь означает гипотезу структурного связующего узла, не установленного руководителя. `terminal` — наблюдаемый конечный получатель в выборке, не доказательство хранения денег. `peripheral` включает неопределённые случаи и не означает «неважный» или «невиновный». Seed показываем отдельным признаком, не выводим его роль из неполных входящих данных.

Для глубины 4 отсутствие выхода не используется как признак удержания денег. Наблюдаемые входящие позволяют назначить признаки консолидации; роль terminal запрещена на обрыве. Сохранять `truncated_by_depth` и отдельное `role_rule=boundary_consolidator` либо `boundary_unknown`, показывать ограничение в evidence и карточке. На пустой подвыборке для квантиля соответствующее правило не срабатывает. Квантили считать с линейной интерполяцией и сохранять полученные пороги.

Почему начинаем с таких порогов: по всем узлам Q95 входящей степени равен 3, исходящей — 5; Q75 входящей суммы — 164 528 KZT. Это ориентиры, не финальные пороги: для правила консолидации Q75 пересчитывается на указанной подвыборке. Не нужно добиваться искусственно равного числа узлов каждой роли.

### Оценка и объяснение

`role_score` — эвристическая сила наблюдаемых признаков с учётом ограничений, **не вероятность причастности или измеренная точность классификации**. Расчёт применяется только после выбора роли. Для фиксированных критериев первой версии:

- Пусть `E(x,t)=clip((x/t - 1)/2, 0, 1)` при `t>0`: 0 на пороге, 1 при превышении порога втрое.
- `consolidator`: `0.55 + 0.15*E(in_deg,3) + 0.15*E(in_kzt,Q75)`; на границе вычесть 0.15 и обязательно сохранить оговорку.
- `distributor`: `0.55 + 0.30*E(out_deg,5)`.
- `coordinator`: `0.45 + 0.15*E(betweenness,Q95) + 0.15*E(seed_reach_count,2)`. Даже высокий результат означает структурную связность, не руководство группой.
- `transit`: `0.45 + 0.20*clip(1-abs(pass_through-1)/0.3,0,1)`. Максимум 0.65 отражает отсутствие доказанной связи входящих и исходящих денег.
- `terminal`: 0.55 — только наблюдаемое отсутствие исходящих внутри охвата; объём не повышает уверенность в удержании денег.
- `peripheral`: 0.20 для остаточного правила, 0.15 для неопределённой границы, 0.10 для изолята. Это низкая определённость роли, не доказанная периферийность.

Коэффициенты — стартовые эвристики команды. Проверить их поведение на крайних случаях и описать в docs/roles.md; не представлять их статистической калибровкой. Все результаты конечны и лежат в 0..1. При изменении порогов синхронно обновить формулы оценки, документацию и проверки.

`evidence`: короткий шаблон по роли, реальные числа, ≤200 символов. Например, формат «Признаки консолидации: вход от {in_deg}, выход к {out_deg}; вход {in_kzt} KZT; порог {threshold}». Для границы — глубина и отсутствие наблюдаемых исходящих; для изолята — 0 входящих/исходящих и недостаточность данных. Не обрезать готовый текст так, чтобы исчезла оговорка.

## 6. Seed-метрики, сообщества, приоритет и выгрузки — участник B

### Seed-достижимость (`seeds.py`, сдать первым, ~40 минут)

Число разных seed, из которых узел достижим по направлению переводов за 1–4 шага (`seed_reach_count`), и минимальная направленная дистанция (`seed_distance`). Считать BFS отдельно от каждого seed, исключая сам seed из его собственного счётчика; seed имеет дистанцию 0, недостижимый узел — пустое значение. Это достижимость, не доказанный маршрут конкретных денег. Нужен A (правило coordinator) и B (компонента S приоритета).

### Кластеры

1. Найти слабосвязные компоненты полного направленного графа.
2. Для каждой компоненты с рёбрами построить неориентированную проекцию: вес пары `{u,v}` равен **сумме** переводов в обоих направлениях. Простое преобразование, теряющее один из встречных весов, не подходит.
3. Запустить Louvain с `weight='sum_kzt'`, `resolution=1.0`, фиксированным `seed=42` и стабильным порядком входных узлов/рёбер.
4. Каждый изолят — отдельный кластер. Проверить связность полученных сообществ; если сообщество несвязно, разделить его по компонентам.
5. Присвоить целочисленные ID после стабильной сортировки кластеров по размеру, затем минимальному gid. Gid здесь только разрешает ничью и задаёт порядок, не определяет содержательную классификацию.
6. Посчитать `n_nodes`, `n_seed`, внутреннюю сумму по исходным направленным рёбрам; выбрать до 5 `top_gids` по рассчитанному приоритету, сериализовать единообразно, например JSON-массивом в CSV-ячейке.
7. `hypothesis` составлять из доминирующих ролей, доли seed и внутренних/внешних потоков, с числами. Сообщество транзакционной связности не объявлять доказанной преступной группой.

### Приоритет проверки

Начальная формула, которую фиксируем до просмотра «интересных» gid:

```text
V = P(out_kzt) для seed; P(max(in_kzt, out_kzt)) для остальных
B = P(betweenness)
S = min(seed_reach_count / 3, 1)
D = P(out_deg) для seed; P(in_deg + out_deg) для остальных
priority_score = 0.35*V + 0.30*B + 0.20*S + 0.15*D
```

`P` — эмпирический процентиль среди положительных значений соответствующего признака по всем узлам; ноль получает 0; равные положительные значения получают средний ранг / число положительных значений. Для V и D сначала формируется одна колонка с указанной seed-поправкой, затем её процентиль. Пустая положительная выборка даёт 0.

Приоритет означает полезность проверки, а `role_score` — надёжность назначения роли: не перемножаем их автоматически. Граница обхода может заслуживать проверки при крупных входящих, но её неопределённость обязательно видна. Seed не получает бонус только за известность; изолят получает приоритет 0.

Сохраняем `priority_volume=0.35*V`, `priority_bridge=0.30*B`, `priority_seed=0.20*S`, `priority_degree=0.15*D`; их сумма равна priority_score. В `why` выводим главные факторы с исходными числами и ограничения, если они влияют на интерпретацию. Top-30 сортируем по priority_score убывающе, при равенстве — по gid. Все узлы, включая seed, допустимы в обязательном top; в интерфейсе отдельно доступен фильтр non-seed.

**Проверка при первом прогоне — доля seed в top-30.** Приоритет не учитывает роль, а для seed V = P(out_kzt), и у seed большие исходящие. Если seed больше трети top-30, список повторяет исходные 81 gid и не выполняет главный тезис ТЗ («фокус смещается с 81 курьера на реальные точки консолидации»). Тогда `top_nodes.csv` строить по non-seed, а seed оставить отдельным фильтром в интерфейсе. Решение и полученную долю записать в docs/ranking.md.

### Выгрузки (`outputs.py`) и проверка контракта

Запись трёх CSV в схеме AGENTS.md, дополнительные колонки для карточки узла. `tests/test_outputs.py` проверяет список из §8 «Интеграционный прогон». C вызывает `write_outputs` из `run.py` и не меняет схему сам.

До заморозки один раз проверить чувствительность: resolution 0.8/1.0/1.2 и небольшое изменение весов приоритета. Посмотреть число/размеры кластеров и пересечение top-30. Это проверка устойчивости, не доказательство правильности и не подбор под ожидаемые личности.

## 7. Экран аналитика и запуск — участник C

Главный сценарий: жюри вводит любой gid → получает роль, правило с порогом, метрики, причины приоритета, ограничения данных и ближайшие связи.

Отдельно показать «Что неизвестно» и «Что запросить для проверки» по шаблону ограничения: например, дальнейшие переводы за четвёртым коленом. Не выдумывать сведения о клиенте.

## 8. Проверки, которые действительно нужны

**Данные и граф:** уникальность gid/пар, известные концы рёбер, конечные положительные суммы и целые положительные количества, согласование сумм/числа транзакций, сохранение всех 19 изолятов. Ошибки входа объяснять явно.

**Небольшие искусственные графы:** цепочка → transit; несколько входов → consolidator; веер выходов → distributor; изолят; настоящий наблюдаемый конец; одинаковая топология конца на глубине 3 и 4; seed с неполным входом. Проверять, что неполные входящие seed не становятся основанием для его роли. Для кластеризации — встречные рёбра с суммированием весов, изолят, раздельные компоненты. Для приоритета — нулевые признаки и ничьи.

Отдельно: сборщик на границе остаётся consolidator с оговоркой и меньшим score; слабый получатель на границе — peripheral, не terminal. Проверить пустые выборки квантилей, нулевой вход, точные границы порогов, конечность score и изменение его силы внутри одной роли. Для пересечения правил проверить объявленный порядок, для вкладов приоритета — равенство их суммы итоговому score.

**Интеграционный прогон на настоящих данных:**

- Ровно 2 248 уникальных gid, множество совпадает с `nodes.parquet`.
- Обязательные колонки трёх CSV имеют нужные имена и типы; нет пустых обязательных значений.
- Роли из словаря; оба score конечны и в диапазоне 0..1; evidence непустое, ≤200 символов, содержит число.
- Каждый `cluster_id` присутствует в `clusters.csv`; размеры и seed-счётчики согласованы; внутренние суммы пересчитаны по рёбрам; `top_gids` принадлежат своему кластеру.
- `top_nodes.csv` содержит 30 строк, уникальные gid, последовательные rank, невозрастающий приоритет и значения, согласованные с `nodes_roles.csv`.
- Два запуска при неизменных входах/версиях дают одинаковые CSV; время полного запуска <5 минут.
- Экран открывается локально; проверены изолят, граница и три произвольных gid.

Отдельно просмотреть распределение ролей, пересечения правил до выбора основной роли и top-30. Если большинство узлов — terminal/peripheral, это само по себе не ошибка: структура выгрузки содержит много листьев. Не заявлять качество классификации, которого нельзя измерить без разметки.

## 9. Что делать только после готовности базы

Приоритет бонусов: временной профиль выбранного узла → концентрация переводов по дням → короткие возвратные связи. Даты в источнике дневные: нельзя заявлять перевод «через несколько минут». Совпадение сумм/дней не доказывает перенос тех же денег.

HITS, дополнительные центральности, сложные модели и масштабная переработка интерфейса не должны вытеснять проверку схем и подготовку объяснений.

## 10. Готовность к сдаче

Готово, когда есть рабочий однокомандный пайплайн, три проверенных CSV, поиск любого gid и сетевой экран, README с формулами/порогами/ограничениями, диаграмма «данные → метрики → роли → интерфейс», актуальный AGENTS.md.

В README обязательно объяснить: ограничение глубины, неполные входы seed, невидимость переводов ниже 5 000 KZT, потерю направления только в проекции кластеризации, отличие гипотезы от обвинения и score от вероятности. Для масштабирования описать переход к приближённому betweenness и более быстрым графовым реализациям после измерений.

Полное ТЗ с критериями оценки — `docs/tz.md`. По таблице оценки 75 из 100 баллов приходятся на соответствие задаче, техническую реализацию и README/воспроизводимость; сначала закрыть обязательный сценарий и его проверки.

Пятиминутное демо: 0:00–0:40 — вопрос аналитика и запуск; 0:40–1:20 — top-30 и причины приоритета; 1:20–3:30 — сборщик, транзит и неоднозначный узел на границе на реальных результатах; 3:30–4:30 — поиск произвольного gid, связи и ограничения; 4:30–5:00 — CSV и следующий запрос данных. Примеры выбирать из рассчитанных результатов; не встраивать их gid в правила. Репетиция включает три случайных узла, а не только заранее выбранные.

Последние 10–20 минут — общий проход: каждый из трёх объясняет любой случайный gid по формуле, числам и ограничениям. Полезность решения на демонстрации определяется этим сценарием.
