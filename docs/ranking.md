# Поток B: достижимость, кластеры, приоритет и выгрузки

Реализация: `pipeline/seeds.py`, `clusters.py`, `priority.py`, `outputs.py`.
Приоритет отражает полезность проверки внутри наблюдаемой сети. Он не
оценивает виновность, полный баланс клиента или вероятность роли.

## Вызовы для участника C

```python
from pipeline.seeds import compute_seed_reach
from pipeline.clusters import assign_clusters, summarize_clusters
from pipeline.priority import compute_priority, make_top_nodes
from pipeline.outputs import write_outputs

# G содержит ВСЕ nodes.gid, включая изоляты; граф направленный.
features = compute_features(G, nodes)                  # поток A
features = features.merge(compute_seed_reach(G, nodes),
                          on="gid", validate="one_to_one")
roles = assign_roles(features)                        # поток A
roles = roles.merge(assign_clusters(G, nodes),
                    on="gid", validate="one_to_one")
scored = compute_priority(roles)
clusters = summarize_clusters(G, scored)
top = make_top_nodes(scored, limit=30)
write_outputs(scored, clusters, top, out_dir)
```

Функции возвращают новые таблицы. Соединение только по gid; индекс таблицы
не является идентификатором клиента. У seeds входные колонки gid/is_seed;
у графа и nodes должно совпадать множество узлов. Веса рёбер sum_kzt
конечны и положительны. У summarize_clusters дополнительно требуются
cluster_id, is_seed, role и priority_score.

**Для интерфейса:** фактические gid превышают безопасный целочисленный
диапазон JavaScript. В Python/CSV сохранять int64; перед передачей в
JavaScript/PyVis/JSON-пропсы графа превращать идентификаторы узлов и концов
рёбер в строки. Не преобразовывать gid через float. Поиск должен сравнивать
точные идентификаторы. top_gids в CSV — JSON-массив целых; читать его в
Python, затем преобразовывать значения в строки для браузера.

## Seed-достижимость

compute_seed_reach выполняет направленный BFS отдельно от каждого seed,
максимум четыре перехода. seed_reach_count — число разных seed, из которых
узел достижим за 1–4 перехода. Сам seed себя не считает, в том числе при
цикле, но может считать другие seed. seed_distance — минимум расстояний;
у seed всегда 0, у недостижимого узла отсутствует значение (nullable Int64).
Изолированный seed имеет счётчик 0 и расстояние 0. Достижимость не доказывает
движение одних и тех же денег по найденному пути.

## Кластеризация

В каждой слабосвязной компоненте строится неориентированная проекция.
Вес пары — сумма переводов в ОБОИХ направлениях. Louvain использует
sum_kzt, resolution=1.0, seed=42 и стабильный порядок узлов/рёбер.
Если сообщество несвязно, оно разделяется на связные части. Каждый изолят
получает собственный кластер. ID начинаются с 0: размер по убыванию,
минимальный gid по возрастанию для разрешения равенства.

summarize_clusters считает внутренний оборот по исходным направленным
рёбрам; встречные переводы учитываются оба. top_gids — до пяти узлов по
приоритету, при равенстве по gid. Гипотеза описывает преобладающие роли,
долю seed, внутренний оборот и видимые переводы между кластерами.
Общая связность не доказывает совместную преступную деятельность.
Оборот суммирует переводы: одни средства могли учитываться несколько раз.

## Устойчивость групп и спорные участники

`pipeline/stability.py` запускается из `run.py` автоматически после основного
разбиения. Десять повторов используют seed 0, 1, 7, 21, 99, 101, 202, 303,
404, 505, неизменные данные, веса и resolution=1. Основной seed остаётся 42.

Для каждой исходной группы в каждом повторе выбирается группа с максимальным
индексом Жаккара: размер пересечения / размер объединения. При равенстве —
группа с меньшим минимальным gid. Сопоставления независимы: две исходные группы
могут сопоставляться одной объединённой группе. Среднее и минимум записываются
в `stability_mean` и `stability_min` в clusters.csv.

Эвристические, заранее фиксированные пороги по минимальному Жаккару: >=0.8 —
stable, >=0.5 — variable, ниже — unstable. Это метки повторяемости состава,
не оценка правильности или вероятности нарушения. Порог не подбирался под gid.

Оценка клиента `cluster_membership_stability` — доля повторов, в которых он
принадлежит сопоставленной группе. >=0.8 — core, ниже — disputed. Ядро может
сохраняться при объединении группы с соседями, поэтому оценку клиента нужно
читать вместе с оценкой всей группы. Изоляты получают отдельный статус isolated,
техническое значение 1, но не включаются в n_core и n_disputed.

На текущих данных: **64 stable, 8 variable, 16 unstable, 19 isolated**;
**2 119 core, 110 disputed, 19 isolated**. Группа 16 имеет 37 core и 4 disputed,
минимальный Жаккар 0.215; у группы 42 все 7 клиентов core, но минимум Жаккара
0.125 — пример слияния с соседями. Пять первых повторов недостаточны для вывода
о полной устойчивости: группа 8 сохранялась в них, но минимум по десяти — 0.342.

Вкладка «Группа клиента» показывает эти оценки, спорных клиентов и наблюдаемые
межгрупповые потоки с разделением входа/выхода. Для спорного клиента наиболее
связанная другая группа определяется по сумме обоих направлений; это подсказка
для просмотра, а не автоматическое переназначение или оценка принадлежности.

### Экспериментальное согласованное разбиение

Для существующих неориентированных рёбер исходный вес умножается на долю
совместных попаданий концов в группу в 11 разбиениях (базовое и 10 повторов).
Рёбра с нулевой поддержкой исключаются; вершины сохраняются. Затем применяется
тот же Louvain по компонентам. Матрица всех пар клиентов не создаётся.

| Показатель на исходном графе | Основное | Экспериментальное |
|---|---:|---:|
| Число групп | 107 | 163 |
| Модульность | 0.85457 | 0.82862 |
| Доля суммы внутри групп | 90.05% | 86.52% |
| Средний ARI к 10 альтернативам | 0.89423 | 0.87467 |

Эксперимент не дал улучшения по выбранным показателям, поэтому исходные cluster_id
сохранены. Это сравнение одной конкретной реализации, а не доказательство,
что любой согласованный метод хуже. Согласие измерено на ансамбле, участвовавшем
в построении кандидата; независимой валидации/ground truth нет. Неполнота выгрузки,
изменение периода, весов и порога отсечения в этих десяти повторах не моделируются.

Диагностика, параметры, сравнительные метрики и длительность сохраняются в
`run_metadata.json` → `cluster_stability`. Полный запуск на текущем окружении
с диагностикой занял **2.03 с**. Обязательные схемы CSV сохранены; добавлены только
диагностические колонки. Оценки и счётчики проверяются writer перед записью.

## Приоритет

Для положительных значений P(x) = средний ранг среди положительных /
количество положительных. Нули получают 0; пустая положительная выборка
даёт 0. Равные значения имеют одинаковый средний ранг.

```text
volume = out_kzt для seed; max(in_kzt, out_kzt) для остальных
degree = out_deg для seed; in_deg + out_deg для остальных
priority_volume = 0.35 * P(volume)
priority_bridge = 0.30 * P(betweenness)
priority_seed   = 0.20 * min(seed_reach_count / 3, 1)
priority_degree = 0.15 * P(degree)
priority_score  = сумма четырёх вкладов
```

volume и degree сначала формируются для всех узлов с seed-поправкой,
затем ранжируются общей выборкой. betweenness должен приходить от A:
направленный, без весов расстояния. Все вклады сохраняются в CSV.
Изолят получает 0. role_score не умножается на приоритет; неопределённый
крупный получатель на границе может требовать проверки.

Входы seed неполны, поэтому его объём и степень берутся по исходящим.
У остальных клиентов также могут отсутствовать потоки извне выборки.
Крупный оборот и посредничество бывают у законных участников: рейтинг
предназначен для проверки гипотез и не устанавливает организатора.

make_top_nodes сортирует priority_score по убыванию, gid по возрастанию.
Согласно Plan.md, сначала проверяет долю seed в исходном top-30. Если она
строго больше 1/3, выбирает top среди non-seed без изменения score.
Диагностика находится в top.attrs: selection_policy, initial_top_size,
initial_top_seed_count, initial_top_seed_fraction. C может сохранить её
в метаданных запуска; attrs не сохраняются автоматически в CSV.
why содержит факторы, числа, вклады и ограничения seed/границы.

## Проверки и наблюдения на данных

На выгрузке хакатона проверены 2 248 узлов, 19 изолятов, 35 полных
слабосвязных компонент. Счётчики достижимости независимо сверены обратным
BFS от каждого узла. Все изоляты получили нулевой приоритет.

При resolution=1.0 получено 107 кластеров, крупнейший — 272 узла.
Все группы связны; внутренние суммы независимо пересчитаны по edges.

Исходный top-30 содержит 4 seed (13.33%): применяется all_nodes.

### Проверка полезности рейтинга

Все 30 лидеров находятся в крупнейшей компоненте (1 877 узлов); граничных
узлов в top-30 нет. У 24 клиентов score >=0.95, у пяти >=0.99: такие числа
означают высокие процентили признаков, а не вероятность нарушения.
Глобальное посредничество и число достижимых seed дают преимущество
крупнейшей компоненте. Это ограничение формулы; полезно дополнительно
показывать лидеров выбранной компоненты и граничные узлы из полной таблицы.
Обязательный рейтинг при этом сохраняет документированную формулу.

Три проверяемых случая (ранги в общем рейтинге всех клиентов):

- `100000000331309100`, ранг 2: вход 984 635 KZT от 5 клиентов, выход
  23 001 375 KZT к 99, достижим из 4 seed. Нельзя утверждать, что все
  исходящие — именно деньги seed. Запрос: полные входящие и начальный остаток.
- `100000002578405100`, ранг 128, score 0.808973: вход 1 200 351 KZT
  от 2 клиентов, выход 3 108 352 KZT к 116. Это лидер второй компоненты
  на 270 узлов; достижим из 1 seed, вклад этого признака только 0.066667.
  Даже максимум получателей не гарантирует место в общем top-30. Запрос:
  полные входящие и дальнейшие переводы получателей; просмотр компоненты.
- `100000001053894100`, ранг 423, score 0.588340: depth=4, вход
  2 000 000 KZT от ОДНОГО клиента, исходящие не наблюдаются; достижим из
  3 seed. Три seed — непрямая достижимость, не три непосредственных
  плательщика. Запрос: дальнейшие исходящие за границей обхода.

Роли этим примерам поток B не назначает. Среди 444 граничных узлов
максимальный score — 0.588340, медиана — 0.275. Их отсутствие в top-30
не является основанием исключать их из аналитического просмотра.

## Выгрузки и границы проверки

write_outputs проверяет обязательные схемы, типы, непустые тексты, диапазоны
оценок, evidence с числом длиной до 200 символов, уникальность gid,
численность кластеров и seed, принадлежность top_gids, порядок top,
совпадение ролей/оценок с таблицей узлов, сумму вкладов и запрет terminal
на обрыве. Затем пишет три UTF-8 CSV в стабильном порядке, сохраняя
дополнительные колонки узлов и разрешённые пропуски метрик.

Функция не получает исходные nodes/edges: точное покрытие исходных gid и
правильность сумм по рёбрам проверяются интегратором отдельно. Для небольших
тестовых графов разрешено min(20, N) строк top, для настоящих данных нужно
не меньше 20 (план команды — 30). Финальная проверка — с настоящими ролями A.

Запуск тестов из корня после установки зависимостей и pytest:

```bash
python -m pytest tests/test_clusters_priority.py tests/test_outputs.py -q
```

Интеграционный тест использует реальные переводы, но явно тестовые роли
для проверки контракта B; CSV создаются только во временной папке pytest.
Они не являются результатом классификации и не предназначены для сдачи.
При отсутствии data тест реальной выгрузки пропускается.
Тест также сохраняет sensitivity.json во временной папке: разрешения
Louvain, изменения весов и пересечения top-30. Для сохранения отчёта по
известному пути можно передать pytest `--basetemp=/tmp/50tenge-b-audit`;
использовать выделенную временную папку: pytest очищает basetemp при запуске.
Входные gid с типом float запрещены до расчёта, чтобы исключить округление
больших идентификаторов и слияние разных клиентов при приведении к int64.
